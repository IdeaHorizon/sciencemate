# Agent 科研平台设计决策记录

> 基于 AI4S平台设计-wangd.pptx 的 47 项设计决策，经讨论确认。
> 日期：2026-04-22

---

## 一、平台定位与边界

### Q1. 平台的自主性定位
**决策：双模式支持**
- **全自主模式**：系统自主推进，仅在系统判定的关键节点暂停
- **辅助模式**：人主导，系统在关键节点汇报，由人决策判断
- 用户可按项目或按阶段切换模式

### Q2. 初始目标领域
**决策：计算驱动科研优先，但保持通用框架**
- MVP 以 AI/ML、计算化学、生物信息等计算驱动领域为首要验证场景
- 架构层保持领域无关，节点/harness/tools 可按领域扩展

### Q3. 目标用户
**决策：全覆盖，分阶段**
- Phase 1：个人科研者（独立研究员、博士生）
- Phase 2：科研团队/课题组（PI + 学生 + 博后）
- Phase 3：企业研发部门

### Q4. 平台输出目标
**决策：加速论文产出 + 加速科研发现/实验成功率**
- 两者并重，不优先其中一个

## 二、Research Graph

### Q5. Graph 构建方式
**决策：系统自动生成，用户确认/修改**
- 用户从任意阶段进入，系统根据输入构建最小 seed graph
- 用户可修改、补充、删除节点

### Q6. 节点连接逻辑
**决策：允许循环的有向图**
- 支持实验 → 分析 → 发现新问题 → 回到 survey → 再实验等循环
- 系统需要检测无限循环并预警

### Q7. 并行分支
**决策：允许，但有上限（最多 N 个活跃分支）**
- N 的具体值可按项目配置
- 需要设计分支的创建、合并、废弃机制

### Q8. Graph 生长触发
**决策：系统建议 + 用户确认**
- 全自主模式下，低风险生长可自动执行
- 辅助模式下，所有生长需用户确认

### Q9. 失败节点处理
**决策：由用户决定（保留/归档/删除）**
- 系统默认保留失败节点并标记状态
- 失败原因和上下文自动提取到 Memory

### Q10. Graph 版本控制
**决策：只记录关键 decision point 的 snapshot**
- 不做全量版本控制，减少存储开销
- Decision point 由 Review/Decision 节点或用户手动标记触发

---

## 三、最小公约节点

### Q11. 节点扩展性
**决策：七个基础节点 + 允许用户自定义扩展**
- 基础节点：Survey、Planning、Experiment、Data Process、Analysis、Writing、Review/Decision
- 基础节点集本身也需要不断迭代优化
- 用户可添加自定义节点类型

### Q12. 节点完成标准
**决策：系统建议完成条件，用户可覆盖**
- 不同节点可有不同策略（如 Experiment 可能有硬性数据完整性要求）
- 具体标准随迭代优化

### Q13. 节点间 Handoff
**决策：系统自动摘要/筛选后注入（Context Slicing）**
- 每个节点类型有对应的 context slicing 策略
- 避免 context 爆炸，也避免用户手动选择的负担

### Q14. Review/Decision 节点是否强制
**决策：系统根据风险评估动态决定**
- 高风险转换（如进入大规模 Experiment）自动插入 Review
- 低风险转换可跳过
- 用户可覆盖（强制 review 或跳过 review）

### Q15. 同类节点并发
**决策：允许但有上限，与分支限制对齐**
- 同类型节点并发数 ≤ 活跃分支数上限
- 防止 graph 复杂度爆炸

## 四、知识库与记忆系统（架构级决策）

### 核心架构：知识库 (Knowledge Base) 与记忆系统 (Memory) 分离

| 维度 | 知识库 (KB) | 记忆系统 (Memory) |
|------|-------------|-------------------|
| 内容 | 论文、新闻、领域公共知识、参考资料 | 决策、结论、经验、规则、偏好 |
| 性质 | "世界知道什么" | "我们知道/决定/经历了什么" |
| 更新策略 | 自由更新，系统可自主检索入库 | 受控更新，关键内容需人工确认 |
| 溯源要求 | 保留原始来源（DOI、URL） | 每条标注产生的操作/artifact/推理过程 |
| 用途 | Context 注入原料，RAG 检索源 | 指导 Agent 行为，影响决策和规划 |
| 分层 | Organization KB / Project KB | Organization / Project / User / Session Memory |
| 跨项目 | 可共享（公共知识） | 默认不共享（项目经验隔离） |

### Q16. Organization Memory 写入权限
**决策：自动从项目中提取 → 人工审批 → PI 最终确认**
- 三步流程确保组织级知识的可靠性

### Q17. Project Memory 自动提取策略
**决策：混合模式**

| 类型 | 策略 | 理由 |
|------|------|------|
| 关键决策及原因 | 自动提取 + 用户确认 | 决策是最高价值记忆，措辞需人确认 |
| 实验参数与结果 | 自动提取 | 结构化数据，提取准确率高 |
| 假设与推理逻辑 | 用户手动标记 | LLM 容易误解推理意图 |
| 失败原因分析 | 自动提取 + 用户确认 | 失败记录价值大但解读需人工校准 |
| 项目规则/约束 | 用户手动设定 | 属于项目配置，不应自动推断 |
| 文献 insight | 自动提取 | 来源明确，可溯源 |

### Q18. 记忆冲突解决
**决策：分层策略**

| 层级 | 冲突策略 | 理由 |
|------|----------|------|
| Organization Memory | 保留冲突，提交 PI 裁决 | 组织级知识影响面大 |
| Project Memory | 保留双版本 + 标记冲突 + 提示用户 | 科研中结论演化是常态 |
| User Memory | 新覆盖旧，保留变更日志 | 个人偏好变化正常 |
| Session Memory | 直接覆盖 | 短期记忆，无需保留冲突 |

### Q19. 记忆过期/衰减机制
**决策：分类管理**

| 记忆类型 | 衰减策略 |
|----------|----------|
| Organization Memory | 不衰减，只能管理员手动废弃/归档 |
| Project Memory - 事实类 | 不衰减，标注记录时间 |
| Project Memory - 判断类 | 6 个月未引用/验证后标记 stale，系统主动提示 |
| User Memory | 不衰减，用户自管理 |
| Session Memory | 会话结束后丢弃，关键内容提示用户是否提升 |

### Q20. 空闲时知识检索
**决策：用户定义 + 系统推断结合**
- 新论文/新闻更新进入**知识库**（非记忆系统），可自由更新
- 检索范围 = 用户定义关键词 + 系统根据 project context 推断的相关领域

### Q21. 记忆可解释性
**决策：每条记忆必须标注完整来源**
- 包括：哪次操作、哪个 artifact、基于什么论文、基于哪次推理过程
- 参考 OpenClaw 的空闲时记忆 refine 机制，但提升到科研级别

## 五、证据链与溯源

### Q22. 证据链严格程度
**决策：分级溯源**
- 事实性陈述：必须硬溯源（关联到具体数据/论文段落）
- 推理性结论：允许软溯源（标注推理依据和置信度）
- **溯源要求优先于尽力完成**：无法溯源的事实性陈述降级标注为"推测/未验证"

### Q23. 无法溯源时的行为
**决策：降级为提供相关参考**
- 不输出无法溯源的事实性断言
- 提供相关参考材料供用户自行判断

### Q24. 溯源粒度
**决策：段落级**
- 引用到论文的具体段落/图表
- 知识库中的内容按段落级索引

## 六、Human-in-the-loop

### Q25. 提问频率控制
**决策：用户设定"汇报等级"（低/中/高）**
- "汇报等级"而非"打扰等级"——体现研究助理向导师汇报的隐喻
- 低：只在高风险决策点汇报
- 中：阶段里程碑 + 高风险决策点
- 高：每个显著进展都汇报

### Q26. 用户不响应时的默认行为
**决策：按风险分级**
- 高风险操作：暂停等待，不自动推进
- 中风险操作：等待设定时间后按默认选项推进，记录日志
- 低风险操作：直接按默认选项推进

### Q27. 通知渠道
**决策：用户自选**
- 支持 Web 站内、邮件、即时通讯等
- 用户可按汇报等级配置不同渠道

### 不可自主执行操作黑名单（补充决策）
无论模式和阶段，以下操作必须人工确认：
- 消耗大量算力的操作（超过预设阈值）
- 删除数据/artifact
- 提交论文/外部发布
- 修改 Organization Memory 或 Organization KB
- 涉及外部 API 调用且有副作用的操作
- 授予或变更权限

## 七、工具与权限

### Q28. 工具调用失败策略
**决策：尝试替代工具，确认无法解决后才汇报**
- 自动重试 → 尝试替代方案 → 都失败后汇报用户

### Q29. Agent 自主安装新工具
**决策：沙箱试用 + 用户确认后正式注册**
- 新工具先在隔离环境中试运行
- 确认安全和有效后用户批准注册

### Q30. 成本/预算管理
**决策：双层预算**
- 组织级总预算 + 项目级子预算
- 特殊操作类型（如 GPU 计算）有独立预算线
- 接近预算上限时自动预警

---

## 八、Artifact 管理

### Q31. 版本管理
**决策：最新版本 + 关键里程碑版本**
- 不做全量版本控制
- 里程碑版本由 Review/Decision 节点或用户手动触发

### Q32. 跨项目复用
**决策：通过 Organization 层共享**
- Artifact 提升到 Organization 层后可被其他项目引用
- 保留引用关系链

### Q33. Artifact 范围
**决策：中间产物也算**
- 包括：实验日志、分析脚本、中间数据、图表、模型、报告等
- 系统自动标记 artifact 类型和所属节点

---

## 九、Workspace 与前端

### Q34. 可视化
**决策：多视图切换**
- Graph 视图、时间线视图、Artifact 视图等
- 用户可自选默认视图

### Q35. 主要交互方式
**决策：混合式**
- 对话用于探索、提问、快速操作
- Workspace 工作台用于项目状态查看、graph 浏览、artifact 管理、review 等结构化操作
- 对话不承载项目真实状态，Workspace 是状态的主载体

### Q36. 移动端
**决策：移动端只做只读查看和通知响应**
- 移动端可查看项目状态、接收汇报、回复关键决策
- 不支持移动端进行复杂操作

---

## 十、协作模型

### Q37. 协作模型
**决策：支持协作，角色权限分层**
- 不同用户权限不同（PI、研究员、学生等）
- 权限影响可操作范围和审批流程

### Q38. Agent 归属
**决策：Project 级 Agent（即 Project Harness）**
- 每个 Project 有一个统一的 Agent（本质上是 harness + 配置）
- 个人差异通过个人 .md / 个人记忆注入 Project Agent 的 context 来实现
- 不存在"每人一个独立 Agent"的概念，避免多 Agent 冲突

---

## 十一、技术实现

### Q39. LLM 策略
**决策：用户可配置模型偏好**
- 系统支持多模型
- 不同节点/任务可用不同模型
- 用户/项目可设定模型偏好

### Q40. Context Engine
**决策：每个最小公约节点有独立的 context engine 策略**
- 每个节点类型定义自己的 context 组装规则
- Context = 相关 Memory + 从 KB 检索的知识 + 节点间 handoff 的摘要 + 当前节点上下文
- harness、skills、tool 配置也按节点类型独立设计

### Q41. 部署模型
**决策：先 SaaS，后续支持私有化部署**

---

## 十二、产品与商业

### Q42. MVP 范围
**决策：MVP 做 3-4 个核心节点**
- 核心节点：Survey、Planning、Experiment、Analysis
- Writing 和 Review/Decision 放入第二期
- 保证核心科研循环可跑通

### Q43. 成功指标
**决策：分层指标体系**
- 终极指标（季度/年度）：科研产出（论文数量/质量）
- 日常运营指标：使用频率/时长
- 质量指标：具体任务完成质量
- 辅助指标：用户自评效率提升

### Q44. 产出形态
**决策：论文和产品并行**

---

## 十三、原则性决策

### Q45. 效率 vs 严谨性
**决策：按阶段**
- 探索阶段优先效率
- 验证阶段优先严谨
- 验证阶段默认开启伦理工具，用户可关闭但系统记录"跳过伦理检查"

### Q46. Agent 能力不足时
**决策：尽力完成 + 标注不确定部分**
- 但受 Q22 约束：事实性陈述无法溯源时，必须降级为"推测/未验证"标签
- 溯源要求优先于尽力完成策略

### Q47. 科研伦理层
**决策：提供工具但不强制**
- 验证阶段默认开启
- 用户可关闭，但系统记录跳过行为
