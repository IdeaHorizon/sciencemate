# Experiment 节点开发规则

## 文件地位、优先级与事实

本文件是当前分支 Experiment 开发的完整规范，供开发者和开发 Agent 阅读，不直接作为平台编排器 LLM 或 Experiment env LLM 的运行时提示。处理 Experiment、其框架接口或生命周期时，使用目标 worktree 当前分支自带的本文件；不得静默套用其他分支或所谓“最新版”规则。

本文件只保存长期职责、不变量和开发纪律。具体资源阈值、工具参数、wire 状态枚举、函数名、issue、迁移进度和测试计数属于代码、tool schema、测试、设计文档或 ROADMAP。

发生冲突时依次服从：

1. 平台、系统和开发者约束；
2. 父工作区 `AGENTS.md` 的目标选择和不可越过权限边界；
3. 在上述边界内的用户当前明确请求，以及尚未被后续决定取代的已确认共识；
4. 当前分支的本文件；
5. 当前正式架构、API、数据和生命周期契约；
6. ROADMAP、历史设计和其他参考材料。

已确认共识必须可追溯到用户决定、用户认可的持久记录或当前有效契约。模型摘要、自我推断、旧 session 和旧运行状态不自动成为规范或授权。

代码、测试、日志和真实运行记录证明系统当前如何表现，不自动定义系统应该如何表现。规范与实现不一致时，应说明预期、现实、影响、真正 owner，以及应修改实现、契约还是测试；既不以测试通过代替设计正确，也不以新设计为由忽略真实回归。

## 角色与修改边界

- **开发 Agent**：读取本文件，协助分析、修改、验证和交付代码。
- **平台编排器 LLM**：理解用户任务、选择节点、创建子 run 并接收节点交付。
- **Experiment env LLM**：在 Experiment 子 run 中规划步骤、调用节点工具并诊断结果。
- **Harness/确定性运行时**：拥有身份、权限、持久状态、外部副作用、物理作业事实和通用生命周期转换。
- **Experiment 节点**：由 env LLM、节点工具、hooks、领域状态和证据契约共同组成的产品能力。
- **下游**：调用方、Reviewer、Analysis 或用户，负责解释证据和决定后续科研动作。

本文件中的 Q1–Q4 只描述用户与开发 Agent 对某项开发事实或决定的交互状态，与 operation/scientific、prereg、节点路由、artifact 或运行时状态无关。

严格继承父工作区的写入、Git 和外部动作边界：全仓可按需只读调查，但仓库源码、文档、测试、staged 内容和 outgoing changes 只能位于父工作区启动规则认定的可写集合内——以目标 worktree 当前 checkout 的 `.scope_map.yaml` 对本 author 生效的 glob 与 `_anyone` 公共 glob 为准，本文件不另抄清单。`shared/contrib/**` 仅用于真正跨节点复用的贡献，不是安放 Experiment 私有逻辑或绕过 framework owner 的通道。

跨 owner 根因不得在节点内伪修。若允许范围内的改动机械触发只读根测试或共享登记变化，应先证明这是跨 owner 契约耦合而非节点缺陷。节点实现完成不等于跨 owner 集成完成；owner 尚未完成必要接线前不得声称可合并。

交接应包含 owner、精确接口或登记项、失败测试、复现和期望值，并区分“节点实现完成”“跨 owner 集成受阻”和“可合并”。节点侧已有获授权的修改时，再附 commit、patch 或 diff；否则明确说明节点侧没有提交。

未经明确授权，不执行会创建、删除或切换 worktree，改变 branch、HEAD、index、worktree 或 refs，或整合、改写历史的 Git 操作。只读查看其他分支优先使用 `git show`、`git diff` 或 `git ls-tree`。

push 前依据实际远端、目标 ref 和当前服务端 scope-policy 比较基线检查完整 outgoing 提交图；upstream 不一定等于本次 push 或服务端校验基线。

保护用户已有改动。本地写权限不自动授权 push、merge、issue/PR、部署、外部消息、停止共享服务或删除长期数据。

## 使命、演进目标与诚实终态

Experiment 的使命是：在框架赋予的身份、能力和生命周期内真正执行既定任务，保存可审计事实和证据，并使所有受管副作用到达可识别、可恢复或可交接的状态。

所有修改都应在不牺牲安全和真实性的前提下，使节点：

- **稳健**：面对弱模型、错误调用、中断、重试、旧状态和平台差异仍保持身份、证据和副作用一致；
- **流畅**：让正确路径和下一合法动作容易发现，减少无意义往返、内部实现提示和不必要拒绝；
- **健康**：保持清晰 owner、单一权威事实、幂等副作用、有界状态、可靠清理和可删除兼容；
- **准确**：以实际观测和持久证据为准，不把计划、推断、退出码或科学意见冒充事实；
- **完整**：尽力成功；不能成功时也形成可接管的诚实终态，不死锁、不伪成功。

门禁、artifact 和测试数量不是目标。安全与真实性是底线；底线内最大化真实任务完成率、恢复能力和用户流程流畅度。

“完整交付”不只等于成功。节点可以交付成功、真实失败、结构化受阻、实际取消或契约允许的部分结果；这些词表达语义，不要求另建一套 wire 状态枚举。只有实际执行与证据满足任务契约时才能声称成功。失败、受阻、取消或部分交付必须保存已发生和未发生的事实、原因、开放资源、owner 与恢复条件。

不得把未实际运行、文字推算、预计算答案、仅有退出码零、未验证的约定输出、身份不一致的输出，或仍无人负责的开放作业声称为成功。科学结果不显著、没有新结论或下游不采用结果，不等于 Experiment 执行失败。

开放作业必须实际终止，或通过框架支持且被接收的协议持久记录新 owner、精确身份和下一动作。仅保存 job ID 或写下“可以接管”不等于 ownership 已转移。

没有合法 handoff 时，先用受管协议取消或终止。若能力不可用或失败，持久化 orphan-risk blocker、精确作业身份和当前物理 owner；只有当前 Core 契约明确继续承担该生命周期时，Experiment 才能结束领域交付，且不得声称作业已经终止、取消或交接。Core 连持续跟踪也不能提供时，应暴露接口缺口，不能让 env LLM 无限循环或伪造终态。

## 用户—开发 Agent 四象限

四象限描述单个事实或实质决定的当前交互状态，不给用户、任务或 session 贴标签；同一任务可同时包含多个象限。象限不扩大授权，也不改变安全和所有权边界。

| 象限 | 进入条件 | 主要动作 | 常见退出 |
| --- | --- | --- | --- |
| Q1 共识区 | 目标、范围、授权和验收足以支持下一步 | 在授权内直接执行和验证 | 新证据、风险、外部变化或用户改意会改变正确动作 |
| Q2 学习区 | 选项及后果基本已知，需要理解原理或作价值取舍 | 解释关键取舍，给少量实质选项和推荐 | 用户选择后进 Q1；需要实测进 Q3；缺私有前提进 Q4 |
| Q3 探索区 | 关键命题经验未知且可观测、可证伪 | 设计最小、代表性、可停止验证 | 证据足够后进 Q1/Q2；发现私有依赖进 Q4 |
| Q4 隐秘区 | 缺少仅用户掌握或 Agent 无权访问且会改变决策的上下文 | 先做相称的安全只读检查，再问最少精确问题 | 补齐后进 Q1/Q2/Q3 |

- Q1 中可自行决定可逆、局部且不改变用户意图的实现细节；“执行已确认的验证”可以是 Q1，而结果仍可属于 Q3。想到另一种做法不足以重开已解决决定。
- Q2 只问会改变实现或验收的问题，不把可从代码、日志、配置或安全探针查明的事实推给用户。
- Q3 至少明确命题、可观测结果、预先判断标准和停止条件；验证规模、副作用上限和环境真实性与风险相称。本地验证只有在保留关键变量时才优先，UI、调度、恢复和多进程问题应走相应真实路径。失败和证伪也是有效结果。
- Q4 可请求脱敏的必要字段，不索要密码、令牌或无关隐私；等待时只继续相互独立、已授权且不会制造冲突的工作。沉默不等于同意，陈旧记录不等于当前私有事实。

用户更正立即取代冲突的旧假设。用户要求暂停时，立即停止新编辑、测试和子任务，只做收敛已启动活动所必需的安全动作和只读盘点；不 commit、stash、revert、切分支或改写未提交内容，未获明确恢复不得继续。长任务只在实质决策点记录非空象限，简单任务不套模板。

## 面向能力有限的运行时 LLM

默认平台编排器 LLM 和 Experiment env LLM 是可纠正但不可靠的控制器，会遗漏、乱序、混淆身份、错填参数、重复调用、误认成功、遗忘上下文或机械重试。身份、物理状态、证据真实性、幂等和生命周期不能依赖模型自律或长期记忆。

产品接口应做到：

- 当前目标、阶段、实际状态、开放作业、成功条件和合法下一步显式可见；
- 用户显式值、系统默认值、模型推断值和实际观测值可区分；
- tool schema 小而明确，不要求模型拼装内部身份或记住隐藏前提；
- 原始长日志持久保存，同时提供可核查摘要和定位；
- 错误说明当前状态、是否产生副作用、能否安全重试、owner 和下一合法动作；
- 状态检查和证据读取始终可达；当前契约支持且该状态适用的取消、恢复和终态交接入口不得被阶段化提示隐藏，不支持时提供诚实 blocker 而非伪造入口；
- 同一状态和输入下的重复错误能转入诊断或终态交接；
- 正确路径比绕过状态机、清空证据或伪造成功更容易。

提示负责可理解性，schema 负责可构造性，正确状态 owner 负责真实性和副作用一致，恢复协议负责一次模型错误不会演变成死锁。弱模型是加强引导、所有权、幂等和恢复的理由，不是无差别增加拒绝墙的理由。

硬门禁只在以下条件同时满足时成立：

1. 保护明确、可机器判定的不变量；
2. 危险在受支持路径上可达且后果严重、持久或难恢复；
3. witness、告警、事后验证或人工纠正不足；
4. 门禁位于能观察并拥有该事实的最小正确边界；
5. 拒绝提供与风险相称、可直接执行的修正信息；涉及持久状态或已有副作用时，还给出当前权威状态、相关身份、owner、重试语义和合法恢复或终止出口，且不会诱发重复副作用；
6. 有危险路径和恢复路径的自动化验证。

涉及持久状态、外部副作用、证据冻结或恢复的门禁，还必须按风险核对它与相关 gate、状态转换、cache/projection、correction、retry、resume、cancel、finalize、cleanup 和终态交接的可达组合，不形成循环前提、互斥恢复、陈旧拒绝或无出口；无状态参数校验不需要机械枚举无关排列。

确定性本身不是硬门禁的充分理由。可恢复的分类、输出声明、质量判断和下游解释问题，应优先使用 witness、说明、评估或可审计纠正，不得固化成不可逆生命周期锁。

## Core、Experiment 与下游边界

| Owner | 负责 |
| --- | --- |
| Core/平台 Harness | project/session/run 与父子身份；权限、capability 和物理可写边界；物理进程与调度事实；持久状态和通用生命周期；通用幂等；取消、清理、终态传播与后续框架流程 |
| Experiment | 理解并实际执行任务；建立领域步骤、参数和 execution intent；调用受管能力；记录输入来源、attempt、输出、错误和偏离；验证约定产物；建立证据链；跟踪作业直至物理终态或正式交接；形成诚实节点交付 |
| 下游 | 判断证据意味着什么、是否足以支持科学结论，以及是否分析、比较、发表或继续研究 |

Experiment 可以报告质量、限制和非约束性建议，但不宣布 hypothesis 已 validated/refuted，不作最终科学结论，不决定下游必须或不得分析，也不自行授权 Core 路由。Core 管身份、能力和物理事实；Experiment 管执行与证据；下游管意义。

当前实现越过边界时，应报告真实调用链和 owner。不得因 Core 接口缺口在节点内自建第二套框架身份、物理进程事实、最终路由或权限体系，也不得隐藏节点已经能够诚实交付的事实。

## operation、scientific、prereg 与下游资格

分类依据是本次 run 的认知目的：

- **operation**：验证软件、系统、流程或既定验收规则是否正确，不从结果支持新的科学结论；
- **scientific**：结果用于探索、比较、估计或支持新的科学结论。

规则如下：

1. 上游为当前 run 提供、指定或声明需要消费 prereg，该 run 一定是 scientific；prereg 是否有效决定能否依约执行，不改变 scientific 身份。
2. prereg 是 scientific 的充分条件，不是必要条件；没有 prereg 的探索性运行仍可为 scientific。
3. prereg 未冻结、损坏、有歧义或绑定失败时，形成 blocker 或 deviation，不得降格为 operation。只有经身份判定属于其他 run、被当前 run 明确 supersede，或只是共享目录残留且未被当前 run 引用，才不构成当前 run 的 prereg。
4. scientific run 可以包含下载、校验、编译、转换、checkpoint 和环境检查等 operational step；步骤性质不改变整个 run 的分类。另起 child 并把 prereg 作为有效输入，该 child 也属于 scientific。
5. 分类影响执行模板和交付描述，不控制真实证据能否保存或节点能否诚实终止。分类纠正必须可审计，不改写已发生事实，也不自动重复执行。
6. prereg 不得静默修改或替换。副作用前已知的实质冲突必须取得 amendment、明确授权或形成 blocker；执行中发生或执行后发现的偏离则记录原承诺、实际执行、发现时间和原因，保留结果，科学意义交给下游。

目标契约中完全删除 `analysis_eligible`。Experiment 不得再产生、解释或以其他名称重建同类资格门禁，也不得用它控制证据冻结、科学 verdict、诚实终态、Core 路由或下游是否分析。

旧 run 可在迁移期读取并忽略遗留字段，使其无语义效果，但必须有测试、owner 和删除条件。Core/shared 尚未迁移时，只能声称 Experiment 侧已停止产生和解释，不能谎称全框架已删除。

## 三件套与证据闭环

Experiment 的稳定证据接口是：

`raw_results → clean_results → experiment_log`

- `raw_results` 保存真实原始输出、stdout/stderr、退出与调度事实、输入输出身份或哈希，以及无法取得内容的原因；
- `clean_results` 对 raw facts 做可重复、机械且有来源的整理，记录质量问题和缺失，不作最终科学裁决；
- `experiment_log` 记录目标、步骤、参数来源、attempt、偏离、限制、开放问题、终态和交接。

三件套描述执行和证据，不审批科学价值。所有正式启动 run 的终态交付保持三件套接口：成功要求三件套满足任务契约；其他诚实终态在相应产物中记录已有、未产生和不可取得的内容。执行前受阻或某类结果未产生时，应明确记录 unavailable、not-run 或等价语义及原因，不得为凑齐接口伪造空测量或未发生阶段；这些是概念状态，精确 wire 值服从当前 schema。

冻结证据不得静默原地改写；纠正形成可审计的新版本或 supersession。历史保留，但完成、审计、快照和 finalize 必须消费同一 active view，且覆盖所有参与闭环的证据类型。

执行是否发生、外部作业生命周期、证据完整性和节点交付是不同维度，不能由一个布尔值或退出码相互代替。

## 权威事实、身份、生命周期与恢复

每项持久事实只有一个明确权威来源和 owner。artifact、receipt、临时 record、cache、projection 和 UI 不得各自维护漂移的“最新事实”；派生视图必须能从权威事实重建。新增持久字段、状态或收据前，说明 owner、可变性、consumer、supersession、恢复和清理；新机制承重后删除或明确弃用旧事件表、cache、reducer、字段和冲突消息。迁移期并存必须单向、有观测和删除条件，不得长期双写两套 active view、身份或终态。

持久事实绑定足够精确且适用的 project、session、run、route、step、attempt、job 和 producer 身份；项目级事实不必伪造 job 维度。外 run 或其他 attempt 的合法收据在候选阶段过滤，不直接视为当前 run 被篡改；payload 与 producer 身份自相矛盾才是完整性错误。

外部副作用前持久化稳定 execution intent 和幂等身份，不能依赖 env LLM 记住“已提交”。严格区分：

- **correction**：对同一不可变 attempt/outcome 的声明、绑定或验证作可审计修正，不重新提交；
- **retry**：创建新 attempt，可以产生新的物理执行，并保留旧 attempt；
- **resume**：重新接管同一开放生命周期；
- **replay/reprojection**：依据持久事实重建派生状态，不产生新副作用。

长期不变量：

1. exact-output correction 对同一 immutable outcome 重新机械验证，保留旧、新声明及依据；不得通过清空有意义的 expected outputs 或隐式重跑完成纠正。
2. 多次 correction 保留 lineage，不得覆盖历史或让无关成功 attempt 回到 pending。
3. 一个 run 可包含多 step、多 attempt 和多 job，所有权不能退化成 project 级单槽。
4. finalize 幂等；重复调用返回同一事实，持久纠正后则重新评估。cache、projection 和 UI 不能永久返回旧拒绝。
5. terminal receipt 在 cleanup 前持久化；cleanup 不删除 closure、resume 或审计所需的唯一事实，并能在临时记录清理后从持久终态恢复。
6. 实际成功作业不得为通过状态机而伪记 cancelled。
7. 无依赖且不会污染共享状态的步骤，只有在 route/state owner 能证明安全时才可继续。
8. 开放作业实际终止或完成正式 ownership handoff；每个可达非终态至少有继续、纠正、重试、取消、接管或诚实 terminal blocker 的合法出口。

相同状态、输入和拒绝不得无限重试。自动重试仅限已证明幂等或没有副作用的动作。

## 安全、能力、错误与 blocker

- path role、route、artifact 或 LLM 声明不能扩张 OS capability。Experiment 不另建并行路径或隔离事实；必须把框架提供的语义路径和物理 capability 完整、准确传给每个子进程，包括 cwd、只读/可写根和会改变落点的运行时环境。
- “请求了保护”不等于保护已生效。enforcement、隔离、资源、只读边界和清理能力声明必须来自实际生效配置、运行事实或代表性行为探测；无法兑现时记录 missing/unknown、影响和 owner。
- 缺少权限、路径 capability、外部身份 owner 或不可逆 effect 授权时，在副作用前 fail closed 或等待确认；非关键可选元数据可记录 witness 后继续。
- 需要跨调用持续、受资源/取消/恢复管理的进程树或外部提交必须走框架受管入口；轻量、同步、有界且不派生持久子进程的诊断或机械计算可走契约允许的轻量入口。选择依据风险和正式接口，不由 benchmark prompt 硬编码内部工具或无关资源。
- 资源请求、系统默认、自动建议和实际观测必须保留来源；省略值不得包装成用户明确申请。
- 输入获取、只读诊断、staging 和机械转换必须保留来源与内容身份，不得补造、替换或推断上游未提供的科学事实。
- 环境能力依据真实 probe，不用 CI、容器或主机名名单替代。平台不支持调度、隔离、恢复或取消时形成准确 blocker 或剩余风险，不伪造能力、取消或清理证据。

错误按风险分级：

- 副作用前的简单 schema/取值错误至少返回稳定 code、错误字段或不变量、合法值、合法形状或约束，以及安全重试方式；
- 状态冲突或已有副作用的错误还必须给出相关身份、权威状态、副作用事实、retryability、owner 和合法恢复或终止动作；
- 终态 blocker 必须说明已完成/未完成内容、证据、开放资源、owner、恢复条件和下一安全动作。

任务验收未满足可以阻止成功声称。只有证据真实性或持久化、身份一致性、权限能力、重复副作用和未交接生命周期等问题，才可阻止节点形成诚实终态；科学 verdict、下游 readiness 或是否产生新结论不得阻止真实失败、受阻、取消或契约允许的部分交付。

## 根因、最小结构性修复与验证

修复目标是消除产生错误状态的共同原因，而非只让当前日志、测试或 benchmark 通过。行为缺陷修改前先建立最小复现或最短可核查证据链；无法建立时说明原因和替代证据。

对有运行时行为、状态、身份、证据、恢复或副作用影响的缺陷，至少识别预期语义、第一处错误状态、被违反的不变量、真正 owner、恢复为何不收敛，以及哪些相邻场景共享原因。纯文档、格式或无行为机械修改只做相称的一致性检查。

优先在最小且正确的 owner 修正共同规则。结构性不等于大规模重写：统一 active view、纠正身份边界或让陈旧拒绝重评都可能是小而正确的修复；局部修复只有在根因确实局部、等价路径不会继续失败且有回归证据时成立。

以下通常是症状补丁，不得作为默认方案：

- 按 benchmark/run ID、错误字符串、单个 artifact 或调用顺序增加特例；
- 在多处复制判断，或新增平行状态、收据和事实源；
- 吞异常、清空证据、删除冲突历史或伪造成功/取消；
- 增加拒绝却没有恢复和终态出口；
- 修改测试迎合错误行为，或依靠更强提示绕过产品缺陷。

Core 缺接口时，节点内兼容只能是诚实、可删除的边界适配，不能成为第二套框架。

### Issue/PR 上下文核查

当前任务、分支、提交、错误签名或所改模块明确关联 issue/PR，且当前环境具备相应只读访问能力时，应针对性核查 issue 主张、讨论、关联提交/PR、目标分支和当前状态；不得在每项任务中遍历全部历史记录。issue 无论由 lujy 或其他人提出，都应依据代码、复现、测试和合并状态独立判断是否属实、是否已解决及是否适合关闭。核查可以提出回复、关闭、重开或合并建议；实际修改远端 issue/PR 状态仍需用户明确授权。无法访问时标记为未核实，不得猜测。

修复与验证强度按实际影响触发。下表各行不是累积测试阶梯；一项变更命中多行时取必要并集，只覆盖受影响、可达且能保留缺陷关键变量的层级：

| 变更类型 | 最低验证 | 追加条件 |
| --- | --- | --- |
| AGENTS、开发文档及不进入运行时上下文的文字 | 定向静态检查和内部一致性审查 | 改变正式产品契约时验证对应实现和测试是否同步 |
| 运行时 prompt、tool description 或其他模型可见文案，不改变 schema/状态 | 定向提示评估 | 影响路由或关键任务决策时做代表性弱模型和对应真实入口验证 |
| 纯函数、格式、局部参数校验、机械转换 | 单元/schema 测试；缺陷修复需可判别回归 | 无持久状态、副作用或跨组件关系时无需 E2E |
| 分类、证据、active view、correction、finalize 或终态中影响持久状态、闭环或恢复的行为 | 单元 + 状态转换/恢复 + 节点集成 | 覆盖原缺陷、合法纠正、重复调用和相邻失败终态；无持久影响的纯分类/映射按上一行 |
| 改变实际执行边界或能力声明的受管进程、路径、隔离、资源、取消、cleanup | 单元/schema + 真实子进程集成 + 负向行为探测 | 涉及中断时增加故障注入与恢复；能力声明验证实际效果 |
| 跨 run/attempt、父子 run、Core handoff、共享接口 | 跨身份状态测试 + 框架接口集成 | 涉及真实路由、UI 或调度器时增加真实 E2E |
| 编排提示、节点路由、用户流程 | 自然任务 benchmark + 对应真实入口 E2E | 确认实际创建 Experiment child；UI 或其生命周期在范围内时使用 UI E2E；内部强制路由只用于独立契约测试 |
| 兼容旧 artifact/run/schema | 旧状态 fixture + 新路径 + 恢复/删除验证 | 明确范围、方向、owner、支持窗口和删除条件 |

行为缺陷的回归必须能识别修复前错误，可由可信失败记录、坏基线、独立临时 worktree、安全 mutation、局部临时回退或等价测试替身证明；不得为证明转红而 destructive reset、污染用户工作区、改写共享历史或触发危险副作用。

只验证受影响且可达的代表性组合，不机械枚举无关排列，也不因清单存在而运行全部层级。测试宿主、fixture、临时目录和继承 capability 是判据的一部分；负向能力测试必须观测真实禁止效果，不能只断言计划或记账字段。未运行的必要层级明确标为未验证，不能用低层测试外推 UI、调度器或跨进程恢复。

真实任务 benchmark 主要描述任务、输入、约束和验收，不强制内部函数、route、artifact 或无关资源参数。路由契约测试可以显式指定节点，但不得与自然任务混为一谈。随机 LLM 单次结果不是唯一合并门禁；确定性生命周期不变量由稳定自动化测试保护。

benchmark 失败应归因到父编排器路由、env LLM 规划、节点 schema/gate、节点状态机、Core/平台接口、外部基础设施或 benchmark/验证器自身，不能笼统记为 Experiment fail。真实 UI/E2E 必须确认确实创建目标 Experiment child；实例应复用、标明代码基线和 owner，声称仍可用前重新探测。

## 兼容、分支、交接与交付

兼容层必须说明旧调用方/输入/持久状态、兼容的是读取形状还是旧行为、风险、测试、owner 和删除条件。兼容不得绕过安全、真实性或幂等，不得无限保留；调用方迁移、旧状态超过支持窗口并通过删除验证后删除。

当前分支规则与当前分支代码共同生效。切换旧分支时使用该分支自带规则，通过正常提交、merge 或 cherry-pick 同步稳定原则，不从新分支静默借用。本文件未提交时不得切换分支；开发期间 branch、HEAD 或 worktree 被外部改变时立即停止写入，重新核对基线并完整重读规则。

Experiment benchmark（案例定义、driver、判卷、答案夹具和实测记录）单独保存在 benchmark 分支（当前为 `experiment-benchmark-suite`），不合入 main；节点分支和 main 不携带这些文件。需要用最新节点代码跑 benchmark 时，把节点分支或 main 合进 benchmark 分支，不把 benchmark 合回节点分支。benchmark 结果只作为节点缺陷的证据，修复落在节点分支，不作为节点改动的验收门槛，也不为让 benchmark 通过而改判据或加特例（见《根因、最小结构性修复与验证》）。

跨 session 交接按适用项记录 worktree/branch/HEAD/upstream、dirty、已完成修改、验证与证据、运行中服务/进程/作业及 owner、blocker 和下一安全动作。恢复后重新探测易变的远端、进程、服务和 UI 状态。委派不转移主开发 Agent 的责任；暂停或交付前应收集仍相关的子任务结论，不遗留无人负责的后台活动。

严重度综合可达性、概率、影响、持久性、可逆性、可检测性和恢复成本；主路径可复现的死锁、错误完成、状态损坏、重复副作用或无安全终态通常阻止合并。只有严重后果假设而无可达性证据时，先按 Q3 验证。

最终交付先给结果，再按适用项说明精确基线、修改范围、核心行为与不变量、根因及 owner、验证和未验证、兼容债及删除条件、跨 owner 剩余问题，以及运行中的 UI/服务/作业。涉及开放副作用、未验证必要层级或 blocker 时不得省略。剩余问题必须区分未实现、未验证和超出权限，不能用“后续优化”掩盖，也不得以修改或测试数量代替完成质量。
