# 已观察输出事实与摘要上限分离

基线：`be025602a831f4642b9496260535ee45194efab9`。本包仅节点内修复，未部署或推送。

## 根因和范围

真实 FVCOM 完整重建的前后快照已完成，但 `diff(limit=200)` 与
`_identity_rows()[:200]` 在持久化时丢弃后面的已观察身份。最终可执行文件即使
已成功重建，也可能只剩上一次构建的旧身份，finish 因此不能认可新交付。
提前声明候选也不充分：created 排在 modified 之前，仍会把目标挤出。

修复在既有 B 观察入口，不改 finish 的成功谓词、任务合同、扫描根或权限：

- 快照预算不变；从已取得的有限快照保留全部 diff 和 changed identities。
- 大观察明细持久写入既有 `capture/<action_id>`，先 fsync，再将带 digest 和
  字节数的相对文件名引用写进原 observation。明细是同一 B 事实的存储，不是新账本。
- 账本与模型/UI 仍是至多 200 条的摘要，明确 `summary_truncated` 和完整计数；
  `truncated` 仅表示实际观察覆盖不足，不再混入展示截断。
- 现有输出投影从 action_started 的 capture 目录（作业使用同一终态记录的目录）
  读取 digest 命名子文件，拒绝路径逃逸、符号链接、内容/大小/owner 不符。
- 缺失或损坏明细变 unknown，不把摘要当完整事实；同观察边界内的旧 producer
  也不能趁明细丢失继续充当当前来源。无关输出根不受牵连。
- 本地 action 与 managed job 的既有观察共用此存储；不增加伪 action，不改调度事实。

小观察继续内联，已存在的内联记录仍能读取。旧大观察已丢失的身份不追认、不补造；
本包不会重新扫描旧运行或改变已冻结交付。

## 验证

- 修复前的 5 格：4 红、1 绿。红格为有/无预先候选的大构建、150 创建＋100 修改、
  managed 260 个输出；绿格为真正快照预算不足时保持未知。
- 新测试文件最终 15 项通过；包含晚到 finish 才点名产物、明细丢失/修改/符号链接/
  路径逃逸、存储失败、并发归属未知、无关根不受污染、受管扫描预算不足。
- 连同真实沙箱边界、目录、身份、账本、managed 相邻测试：81 项通过。
- 恢复旧 `_identity_rows()[:200]` 的进程内变异：四个关键正例全部转红。
- 较宽 `-k 060`（增加最后两格前）：703 通过、3 跳过、5 xfail，唯一失败是已披露
  的 `test_failed_output_is_not_rehabilitated_by_method_correction[object-omitted]`。
  未改该测试，也不声称本包解决任意 shell 的真实读取依赖问题。
- 三组根门禁：17 通过、2 失败（基线已有 registry 欠账、旧工具名提示）；四个生产
  文件按现有 AST 扫描逐一与基线对照，拒绝点数均不变。
- 独立只读审查未发现本包新增阻断项。1000 个小文件的完整目录核验通过，实测
  约 2.77 秒；这是一次观察，不是性能承诺。

## 保留边界

实际快照超预算、读失败、已知并发窗口仍可能无归属；持久化失败仍交既有
`effect_recording_uncertain`，不得重跑副作用。前后快照不是系统调用级写入追踪。
本包不解决 fetch 的 after-only 来源、MPI 通信、父节点额外条件、object-omitted、
大文件同身份原地写入的可观察性。未重跑完整 FVCOM、真实 Slurm 或 UI 模型任务。
当前逐成员核验会重复读取同份明细，大目录仍有平方级读取成本；如需优化，应在
单次 finish 的既有事实视图内复用解析，不用跨调用缓存掩盖证据删改。本包未扩改 finish。

涉及生产文件：`capture.py`、`action_boundary.py`、`ledger.py`、`job_settlement.py`。
`finish.py`、Core、现存实例与现场证据均未修改。
