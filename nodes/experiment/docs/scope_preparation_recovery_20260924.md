# Scope-neutral completion and preparation recovery

## 基线与原则

基线：`22ae44d28ac09dd1f72cbeeea7881cb3364d092f`。本修复在独立分支
`codex/060-scope-preparation-fix` 开发，不改正在服务真实用户的旧检出。

用户 2026-09-24 再次确认：scope 不应成为收尾手续。贯彻 A/B/C，而不是
为每个案例加例外：A 的任务和真实约束决定验收要求，B 的物理事实支持或反驳
C 的交付主张；分类只提供描述和方法选择，不能成为第四套授权或完成状态。

没有 prereg 不等于 operation；unknown 仍是 unknown。没有标签不等于没有证据，
有标签也不能替代证据。真实合同变化、实际消费输入未通过、输出不匹配、失败
反证及开放副作用不因撤分类门而获豁免。

## 证据链和修复

### 1. 做完却被 scope 拒绝

真实 UI 的 CMake 和转换任务已执行并有可核产物，却在 finish 被
`scope_undecided` 拒绝；它们未传内部 typed scope。Core 的合同只有
`intended_use` 自由文本，不能用关键词猜成权威 scope，也不能要求父节点补分类手续。

这不是单一报错分支：原 finish 前置拒绝、authority gaps 和 transaction validator
三层都排斥 unknown success；每轮状态视图还声称 success 不可达。此次一并撤除：

- unknown 和纯 scope 描述冲突只写 limitations；实际任务/输入冲突仍核验；
- success 继续按 required 证据、执行事实、无反证及无开放副作用判定；
- 冻结、恢复、回读接受同一 unknown success，不改写已封存交付；
- 参数见证检查由真实 prereg 绑定承重，错误 scope 标签不能跳过它；
- 删除 action 前的额外 scope 澄清事件；一页纸与每轮视图不再要求补分类。

### 2. 获取源码被退役分类门挡住

下载已进入 v3，却仍调用旧 `audit_execution_intent_binding(require=True)`，
后者依赖旧分类收据并提示调用已退役的 classify 工具；返回内容又误称上游漂移。

v3 获取输入改用既有 A 的只读 selected-task binding 核验，不新建 receipt。
分类未知、未消费的 prereg pending/invalid 不再阻断准备；真正的 Core 合同
身份不匹配及已记录的任务替换仍拒绝。非 v3 路径不迁移旧状态。

HTTPS、出网授权与跳转检查、写入根、容量/超时、hash/commit、不可覆盖导入及
durable-before-spawn 保留。路径解析不再提前 mkdir，目录创建归入已记录 action。

### 3. 重试顺序由随机 ID 决定

新的真实进程回归在失败 exit 7 后成功 exit 0，偶发仍被记为未恢复失败。
`ledger.project_actions` 把事件按随机 action ID 排序，而 finish 按列表先后
寻找后续成功。这既可能误拒恢复，也可能拿失败前的成功抹掉后发生的失败。

在唯一投影 owner 保留规范事件流顺序，不改写历史，不按 ID 或具体案例加例外。
两条确定性反例同时覆盖“失败后成功”和“成功后失败”，另保留真实子进程重试。

## 后续复审：恢复身份与恢复证据

复审以 `1a7be4ea` 为起点。以下两条从只读疑点补成了可执行反例，不能用上轮
节点全绿否定它们，也不能把“排序已修”扩大为“恢复关系已正确”。

- **任务身份恢复退化**：真实 `State.reopen` 后由 Core 覆盖 node inputs，正常
  ready hook 未核对无 Core 身份的 A。任务正文、required、prereg 声明和上游
  材料四种变化都可通过下载入口。复现未手工再次调用 establish；下载进程用替身
  计数，防止测试出网。首轮 4 红 / 3 绿。
- **既有恢复关系漏洞**：真实失败进程写产物后，同目录无关 print、touch、
  另写文件或仅修两件之一可清掉失败；跨 cwd 的真实新产物恢复却可能误拒。
  所有载荷经本地执行工具跑真实进程，首轮 5 红 / 1 绿。

修复分别落在 A 的现有 bootstrap 索引及 finish 对当前交付证据的共同消费处：
不恢复分类门，不造新任务权威，不要求模型提供内部关系 ID。原任务指纹不含
scope/category；同一 prereg 的可用性变化不算换任务；错传后恢复原输入仍可继续。
失败动作仍贡献当前 required 内容或身份时，普通成功命令不能洗白；真正的新产物
和预定检查可以支持交付，旧失败不删除、不被改写为成功。

验证边界：任务身份检查目前覆盖正常恢复 hook 与下载入口，不等于所有 writer
已统一任务变更准入；失败恢复修改只涉及本地 action，不外推受管作业 retry。
预定的一般检查不能豁免仍来自失败 producer 的 required 文件，精确的验证关联
仍需后续设计。自然语言验收接线仍未实现。不能据此宣布节点整体可合并或 UI 已通过。

## 已确认但本包没有掩盖的下一处接缝

真实 CMake 的 `experiment_spec` 已完整写明步骤、验收规则和交付文件，但
只有任务正文，没有 `required_outputs`。当前 obligations 只读取结构化列表，
没有把正文验收接入；bootstrap 允许 ready，后续 finish 会遇到
`obligations_not_frozen`。因此不能把本包等同于这些真实案例已端到端修好。

这不是用户未提供要求。删除该保护并事后以成功产物倒推成功标准同样不正确。
下一项要解决的是“正式任务要求如何成为可执行核验”，不是再次要求用户填表。
应先明确任务解释与机械核验的职责：固定原任务与约束，保留模型对其专业解释及
每项证据关联；机器核验身份/执行/约定检查，不冒称机械证明任意自然语言完整性。
具体协议需按此边界设计，不能用默认 operation、默认全满足或清空验收来绕过。

用户随后提供了另一会话在 `1a7be4ea` 上的两条真实复测摘要：tilepack 和 CMake
实际执行通过，scope 拒绝消失，但均因 `obligations_not_frozen` 以 partial 交付。
这与上述已披露缺口一致；本轮恢复修复不解决它。此摘要由用户提供，本轮未重新
运行其 UI 案例；旧 benchmark 的 50/100 又受 raw-results 格式兼容影响，不能
将分数直接解释成载荷执行失败。下一工作项优先处理验收接线，不继续扩展 scope。

### 自然任务验收的下一项设计边界（待实现，非完成声明）

后续接线工作见 `natural_task_verification_20260924.md`。下文保留本次修复前的
设计边界，不代表后续包仍未实现；实现与真实验证状态以该后续记录为准。

当前缺的是任务理解到核验的连接，不是再加一层分类或让调用方补内部字段。
应分清三件事：

1. 用户原文、正式输入与显式成功条件属于 A，必须保留原文和来源，不能由模型删减。
2. 把这些要求落实为哪些检查，是 Experiment 的专业任务理解；检查方法可以随环境
   和诊断调整，不能将任意调整冒充用户改了要求。已有结构化条件可直接复用。
3. 检查是否真的运行、结果和产物属于谁，是 B；“满足了哪条要求”的解释是 C。
   确定性运行时能核实执行、身份及具体检查结果，不能声称机械证明任意自然语言
   要求已经完整覆盖。

最小目标是把专业核验融入已有执行与交付调用，而非增加必经的声明工具或
强制父编排器填 `required_outputs`。设计需明确任务原文与可执行检查的关联、
检查结果如何进既有行动事实，以及缺少覆盖时如何披露。不能在 finish 看到
什么结果，就倒推这次本来只需要什么结果；不能把“没有内部数组”说成“用户没有要求”。

下一包必须同时验证：清楚的自然任务无内部字段也能完成；少交一项不能成功；
错误结果不能靠降低期望通过；合理更换核验方法无需重跑已完成工作；真实含糊时
只询问具体业务歧义；结构化正式要求和 prereg 不被模型解释覆盖。

现有 governing 将 required 的机械表示与 A 一并预冻结。上述连接如何支持
专业解释与方法调整，需要在实现前明确收口；本包不悄悄改变这个契约。

另有既存共同边界：部分 writer 在 closure 后是否仍可调用，未在本包另造状态机；
Core 完成判定、父子传播及 reviewer 迁移亦不属于本次节点修复完成声明。
