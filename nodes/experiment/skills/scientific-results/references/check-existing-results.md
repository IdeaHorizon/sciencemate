# 检查已有结果

用于内容验收、检查脚本编写和检查失败诊断；科学计算、构建安装、数据整理都可使用。
它不改变原任务、正式条件或权限，不要求为小任务建立新的验收体系。

## 把生成和检查分开

验收入口读取这次执行已经产生的文件并断言要求是否满足。不要调用生成结果的主程序、
安装器或带顶层副作用的模块来“顺便验证”；即使重写后的字节相同，也是在重新执行而不是检查。
把生成器复制到另一目录再运行仍是重新生成。原任务只要求验收已有结果时，已从代码看出
顶层写入就足以排除这个检查入口，不必通过实际重写来证明它有副作用；不能把“附件字节未变”
代替“没有重做计算”。父任务给的可选示例也要与原始要求核对，不能将副本重跑当成只读验收。
只有确认入口本身不改输入、结果或环境时，才把它作为 `finish` 的只读 check。
测试套件需要编译、建缓存或临时文件时，在正常执行阶段按权限运行并保留日志；收尾检查读取
它已产生的证据。framework 自己保存检查记录不等于检查命令可改业务文件。

先看检查代码实际做什么，再运行；不因文件名是 `verify.py`、参数叫 `--check` 或上次退出码为零
就认为只读。错误也可能在检查器：发现问题时修检查逻辑，保留原输出，不先重跑全部载荷。

## 选择对的记录，再作判断

- 从任务要求和实际输出格式确定文件、表/节、字段与记录身份；输入表、标题、汇总行、历史日志
  和本次样本不是同一批数据。解析 CSV/JSON 等结构化输出时用相应解析器与字段选择，不在整个
  目录或混合日志里数数字/行。需要完整矩阵时核对条件组合及重复数，不能只看总行数。
- 绑定实际使用的输入/配置/程序与本次输出。副本哈希相同只证明字节相同；不同 PID 或时间戳
  不自动否定数值一致，不同 run 的结果也不能因内容接近就替代本次必需证据。
- 数值检查采用任务允许的单位、容差与精度；在代码中比较数值并输出稳定的结果标记，避免把
  浮点文本的显示形式当精度判断。先检查会影响结论的缺值、非有限值或重复键；不要为了容错
  默认补零、静默丢记录或忽略解析失败。没有依据时说明未知，不自定宽松阈值。
- 文件存在、非空、退出码零、数值正确和任务完整是不同主张。空 stderr 可以是合法结果；
  “允许空文件”不等于证明它确实零字节。需要哪项就实际检查哪项，不把其中一项替代其他要求。

## 检查失败时先区分对象、方法与实际错误

1. 查看首个失败断言及其实际读到的数据，确认检查的文件、记录集合、单位、输入参数和参考条件。
2. 若参考值与输出冲突，用实际输入核实参考值的适用条件。简短独立推导、已知特例或成熟参考
   实现都可用；不要复用被测公式自证，也不要仅因标着“参考”就重写正确输出来迎合它。
3. 检查器选错记录、用了不支持的选项或误解格式时，改检查器并对原输出复查；正式条件确有
   冲突时原样披露，不能擅改它。程序/输入真的错误则只重做受影响工作，保留先前失败与修正。
4. 选择最可能抓住本次错误的反例。例如计数脚本应能区分输入行和结果行；可在独立的诊断小样本
   上确认错误值或缺失组合会被拒绝，不改真实结果做负向测试。不是每个任务都要穷举测试。

检查规模与尚未证明的主张相称：格式明确的小表通常一次结构化读取和几项断言即可覆盖要求。
复用这份检查及输出，不为每条建议另建一套脚本、对照目录或反例矩阵；只有实际疑点或较高风险
才扩展测试。证明附带旧程序“不够好”不是默认的交付要求。证据已足够就收口。

原始结果和检查已成功、身份仍匹配时直接复用，不因报告排版或收尾元数据变化反复运行科学载荷。
如检查被框架拒绝，保留返回事实，使用它支持的真实只读方式或披露未验证部分，不把重写/重算
包装成无副作用来获得通过。
