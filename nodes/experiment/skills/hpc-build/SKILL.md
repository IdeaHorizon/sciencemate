# HPC 构建与运行诊断

构建时的自然循环：**读目标版本的官方资料与源码说明 → 探测工具链 → 构建 → 看真实日志与产物 →
做有依据的受限修正 → 验证**。框架自己记录每次命令做了什么、写了什么；你不需要为
动作登记、声明或记账，只需要把工作做对。

已有程序的布局或性能诊断从已给记录开始，跳过不适用的构建步骤；只要求分析时，
不默认重建或启动新作业。区分记录已经证明的缺陷、仍待核实的原因和建议的下一步。

复杂构建（多组件、MPI/GPU 变体、需要交调度器的长编译）先在白板上写一份可调整的
专业计划：官方入口与依赖 → 工具链与环境 → 配置 → 构建 → 测试/运行 → 产物核验，标出
每阶段怎么验证、失败了往哪分支。这是你的工作假设，事实变了就改它；小构建直接做，
不用先写计划。跳过不适用的阶段不是违规。

任务涉及 rank/thread 布局、affinity、伸缩、吞吐或性能回退时，按需读取
[并行布局与性能诊断](references/parallel-performance.md)：
`load_skill(name='hpc-build', asset='references/parallel-performance.md')`。
它从已有记录开始，给出布局核对、可比测量和瓶颈分流方法；不要求为了诊断默认重跑。

上述本地方法与目标版本官方资料仍不足以支持当前专业决策时，再按需利用
[外部方法来源](references/external-method-sources.md)：
`load_skill(name='hpc-build', asset='references/external-method-sources.md')`。
外部入口是补充来源，不要求每次检索、安装技能或执行整套上游流程。给出具体参数组合
或核验预期时，若现有依据不足以确认目标版本语义，按需核对官方资料；未核实的内容
标为候选，不把看似合理的命令或数值关系当成已确认的方法。

1. **明确任务与官方入口。** 确认软件、版本/源码 revision、目标平台，以及用户要的是
   编译、安装还是运行验证。按需要查该版本官方文档、源码说明与构建配置，核对入口、
   参数和依赖；已有可靠信息直接复用。不能仅因看见 Makefile 就假定裸 `make` 正确。
   复杂任务在白板记关键依据和预期产物，不把整理资料变成每一步的前置手续。
2. **在影响选择时咨询能力。** MPI/GPU/ABI 或资源选择有关键未知时，用
   `preflight_build_resources` 等现有观测缩小范围；它是建议，不是编译准入。
   已安装、已有授权、工具入口支持、目标环境实际可运行是不同事实。宿主机发现
   launcher 不证明执行环境能 MPI_Init；需要运行时再做有界代表探测，纯编译任务
   不因此追加 MPI 运行要求。复用仍适用的结果，环境变化后刷新相关项。
   上游明确给出 CPU、内存或 walltime 时逐值遵守，不偷偷加余量。
3. **遵循官方层级**：官方构建系统；带官方文档变量的官方构建系统；针对已观察失败的
   官方文档；最后才请求方向。不把依赖图替换为手工逐文件编译，也不在失败后无证据地
   换入口、改用裸 `make` 或后台任务。
4. **工具链可追溯且兼容**：保存实际编译器、MPI wrapper、链接库、launcher 和关键
   配置的来源/版本。可复用 case-local 环境脚本（如 `env/build_env.sh`）、模块配置或
   官方 preset，确保主要命令使用预期环境；不把某个脚本路径或同一安装目录当成兼容证明。
5. **在实际获准的可写位置构建**，保留只读源码基线。构建目录、工具路径和 cwd 遵循
   框架已有能力，不由本 skill 新定义路径角色或扩大权限。保存源码身份、配置/构建命令、
   关键环境、原始日志、产物路径及 patch/diff，复用已有记录而不重复抄写。
6. **按阶段实际产物核验并正确复用**：检查应有的配置、库或可执行文件，不以退出码零
   代替产物证据。保留载荷原始退出状态，避免后接 `echo` 等命令将失败覆盖成成功。
   没有新证据不重复已通过工作；源码、宏、编译器、ABI 或依赖变化后，按构建系统规则
   重新配置/重建受影响部分。无法确认旧对象或缓存适用时，采用官方重建方式或新构建树；
   不默认增量链接证明配置一致，也不每次无差别全 clean。
7. **失败先分层，一次只诊断一层**：环境、依赖、参数、源码、资源或运行时；编译、链接、
   运行环境、配置、运行。提出可证伪的原因，做最便宜的区分性探测，进行一项受限修改并
   验证。反复失败时改变假设、记录 dead end 或请求帮助，不重复同一编辑、不无依据换路线。
   优先利用适用 skill、目标版本官方文档及对应 Spack recipe 的依赖/变体/补丁线索，
   只采用与当前版本、工具链和真实错误相符的修法；它们不必按固定顺序逐份查完。
   每次重试说明改了什么、要区分什么；同错误无新信息时换假设或请求帮助，有新证据时
   允许继续诊断。失败次数不自动证明路线永久无效。
   临时观察先记在现有白板/工作记录中，带环境、版本、证据和重新尝试条件；稳定且值得
   沉淀的知识才按现有 `create_claim` 契约写项目级记录（含 `claim_text` 等必需字段）。
   不直接创建组织级知识，也不把一次平台限制推广成跨平台禁令。
8. **按本次任务选择运行检查**，不是所有二进制都要通过同一套预检：
   - **依赖与加载**：动态程序核对目标平台的依赖解析；可信 ELF 可通过 shell 命令
     `ldd <binary>` 辅助检查（它不是框架工具）。
     静态或非 ELF 程序使用适合其格式的方法，不因不适用的 `ldd` 失败判构建失败。
     缺库时定位对应库与兼容版本，只调整需要的 case-local 搜索路径，避免混入另一套运行时。
   - **MPI（适用时）**：核对实际链接 MPI 与 launcher 的兼容性；Slurm `srun` 还需匹配
     PMI/PMIx 接口，不能只比较安装目录。运行使用目标应用与平台支持的方式；上次在另一
     环境成功不能替代本次证据。纯串行程序不加 MPI 检查。
   - **工作目录与输入**：依据程序实际读取/写入方式选择已获准 cwd，核对输入和输出位置；
     工具参数路径与 shell 内相对路径各遵循其既有坐标，不以 skill 绕过框架拒绝。
   - **任务内容**：需要模拟时核对适用的单位、参数、步数/时长及实际输出；不凭单个字段
     为零就断言空转，非模拟任务不套 namelist。用户/正式输入约定的数值或收敛检查照做，
     不为通过检查缩短任务、改物理参数或以串行替代要求的 MPI 运行。

编译、链接、启动和科学算例验证分别报告证据。只编译的任务可交付构建结果并说明
运行未验证；要求运行的任务缺启动或数值证据就不能称全部完成。环境先阻断只说明
后续阶段未验证。对照程序在同一环境与最早阶段复现相同错误或能力限制，只支持
“当前 first blocker 属环境/平台”的有界判断；不证明目标二进制越过该点后无 ABI、
配置或运行问题，更不能称“唯一障碍”。
改变编译宏、所链接的 MPI 或串并行模式而重建的产物只作非等价诊断旁证，不替代目标
产物的运行验收；若仅换站点支持且兼容的 launcher 并实际运行同一目标二进制，可按实际
覆盖范围记录该产物的运行证据。
检查结果和限制随现有 `finish` 交付，不加表单。

有界、同步、几分钟内出结果的 configure / build / test 直接 `safe_run_bash`；会活过本次
调用、需要受管调度与恢复的长构建使用当前实际支持的 `submit_job` 能力（按需读
`scheduler-longrun`）。命令存在或 dry-run 成功不等于真实提交可用；入口受阻时报告
具体缺口，不用 shell 直接提交来绕开受管边界。
优先使用 case-local 环境变量、构建配置与 overlay，而不是移动或删除系统/conda 文件。
生成缓存可以重建，但可复现的修复必须落在官方或 case-local 配置接口中。
本 Skill 不授权 GPU 假设或科学 verdict；涉及这些问题时加载对应 Skill。
